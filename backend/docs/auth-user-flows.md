# 인증·계정 관리의 전체 흐름 검증

[#78](https://github.com/Daebangg/sayroam/issues/78)은 화면별 검사를 연결해 가입부터 탈퇴까지의
상태 전환을 확인합니다. 실제 서버·메일을 사용한 결과와 응답을 제어한 브라우저 검사를 구분합니다.
자동 검사 통과나 공급자 로그인 화면 도착만으로 실제 소셜 로그인 완료를 기록하지 않습니다.

## 반복 실행하는 자동 검사

```bash
# 저장소 루트: 임시 MySQL·Redis, 메일 수집기를 사용하는 전체 빌드·테스트
./backend/gradlew -p backend build
# 같은 계정의 전체 수명주기만 확인
./backend/gradlew -p backend test --tests '*AuthIntegrationTests.emailAccountLifecycleKeepsRevokedLoginsInvalidAfterResetChangeDeletionAndRejoin'
# frontend/에서 실행
pnpm check
pnpm build
```

`emailAccountLifecycleKeepsRevokedLoginsInvalidAfterResetChangeDeletionAndRejoin`은 같은 이메일로
가입 → 로그인·Refresh → 로그아웃 → 비밀번호 재설정 → 비밀번호 변경 → 탈퇴 → 재가입을 연결합니다.
각 단계의 다른 기기 로그인, 이전 비밀번호 거절, 인증 버전 누적, 개인정보 정리와 재가입 후 이전
Access·Refresh의 거절을 확인합니다. 재가입한 회원은 새로운 ID를 사용하고 이전 방 멤버십을 물려받지 않습니다.

여정 중 Redis 전체를 초기화하지 않습니다. 비밀번호 변경·탈퇴가 공유하는 발송 대기 시간의
429 응답을 확인한 뒤 해당 cooldown만 만료시킵니다. 재가입도 가입 메일 cooldown만 만료시키며
발송 제한 카운터가 유지되는지 확인합니다. 개발 DB·Redis·SMTP와 개인 계정은 사용하지 않습니다.
개별 실패·동시성 검사는 [인증 테스트 안내](auth-testing.md)의 기존 검사와 함께 실행합니다.

## 실제 서버·메일·브라우저 확인

2026-11-10에 local Spring Boot, Vite, 개발 MySQL·Redis, 실제 SMTP와 Gmail 수신을 연결해 확인했습니다.
실행 서버의 OpenAPI와 저장된 프론트엔드 계약도 일치했습니다. 메일 주소·인증 코드·비밀번호·토큰은
이 문서와 테스트 코드에 기록하지 않습니다. 기존 계정과 구분한 일회성 메일 별칭으로 가입했고 해당
테스트 계정만 변경·탈퇴했습니다.

| 사용자 흐름 | 확인 결과 |
| --- | --- |
| 비로그인 회원 화면 직접 접속 | 로그인 안내를 표시하고 회원 정보를 노출하지 않음 |
| 메일 수신 → 가입 → 로그인 | 실제 수신 코드로 인증 200, 가입 201, 로그인·내 정보 200, 원래 계정 화면 진입 |
| 새로고침 → 로그아웃 | Refresh 200·내 정보 200으로 복원, HttpOnly Refresh 확인, 로그아웃 204 후 회원 화면 차단 |
| 비밀번호 찾기 | 로그아웃 상태에서 메일 인증·재설정 204·새 비밀번호 로그인 확인. 별도 기기의 기존 Access·Refresh는 각각 401 |
| 계정 설정의 비밀번호 변경 | 목적별 실제 메일 인증·변경 204·새 비밀번호 재로그인 확인. 다른 탭이 회원 화면을 정리하고 다른 기기의 기존 Access·Refresh는 각각 401 |
| 계정 삭제 | 목적별 메일 인증·복구 불가 확인 후 삭제 204, 공개 화면 이동·완료 토스트 확인. 이메일 익명화·로그인 수단 삭제를 DB에서 조회하고 이전 Access·Refresh·로그인은 각각 401 |
| 잘못된 코드·발송 제한 | 실제 서버의 코드 오류 400 및 발송 제한 429에 맞는 안내 표시 |

탈퇴 후 공유 기록 보존·동일 이메일의 새 ID 재가입·모든 이전 로그인 거절은 서버 통합 검사로
확인합니다. 위 브라우저 여정에서 실제 재가입까지 수행한 것으로 해석하지 않습니다.

## 응답을 제어한 브라우저 확인

실제 API와 별도인 브라우저 문맥에서 가입 관련 응답을 제어했습니다. 실제 수신·DB 변경 검증에
합산하지 않으며 테스트 메일 주소는 `example.test`를 사용합니다.

- 짧은 코드 유효시간이 끝나면 남은 시간 0·만료 안내·코드 확인 비활성화를 표시하고 새 코드를 요청할 수 있습니다.
- 발송과 가입 완료 버튼을 각각 연속 클릭해도 요청은 각각 한 번만 전송합니다.
- 가입 완료 응답을 통신 실패로 만들면 결과 불확실·로그인으로 결과 확인 안내를 표시하고 오류에 포커스를 옮깁니다.
  같은 증명으로 완료 요청을 반복하지 않으며 새 이메일 인증부터 다시 진행할 수 있습니다.
- 계정 작업의 증명 재사용·목적 혼용·응답 유실은 `frontend/scripts/account.test.mts`, 로그인·복원·로그아웃의
  동시 요청·지연 응답·실패 복구는 `auth-state.test.mts`, `auth.test.mts`, `refresh.test.mts`,
  `cookie-coordination.test.mts`로 함께 확인합니다.

대표 화면은 데스크톱 1440×1000과 모바일 390×844에서 확인했습니다. 한국어 밝은 테마와 영어 어두운
테마의 긴 입력·유효성 문구·버튼·모달 내부 스크롤에 가로 넘침이 없었습니다. 키보드 이동 중 배경의
컨트롤로 진입하지 않고 Escape로 닫으면 로그인 진입 버튼에 포커스를 복원했습니다.
화면 캡처는 저장소에 포함하지 않습니다.

## 소셜 인증과 추가 확인 조합

세 공급자의 계정 선택 화면 리다이렉트는
[#74의 사용자 확인](https://github.com/Daebangg/sayroam/issues/74#issuecomment-6764522807)을 재사용합니다.
이번 검증에서도 Google의 실제 로그인 화면 도착을 확인했습니다. 자동 가입·기존 이메일 계정 연결,
이메일 누락·취소·실패·일회성 결과 처리는 서버 통합 검사와 `social-auth.test.mts`로 확인합니다.

사용자는 별도 직접 인증을 완료했다고 확인했습니다. 이 결과는 사용자 확인으로 기록하며,
공급자·신규/기존 계정·동의 상태별 상세 조합을 모두 재현한 결과로 확대하지 않습니다.
다음 조합은 위의 화면 도착·자동 검사·사용자 확인과 구분해 추가 확인합니다.

- 실제 Google·Kakao·Naver의 기존 회원 로그인과 신규 자동 가입 완료
- 이메일 동의 누락 후 재동의와 서비스 복귀, 공급자 화면에서 직접 취소한 뒤 재시도
- 실제 공급자 인증을 마친 뒤 원래 화면 복귀·결과 fragment 정리·새로고침 시 중복 소비 방지
- 실제 재가입 메일 수신부터 새로운 계정 생성까지의 브라우저 여정
- 실제 SMTP 장애·DB 커밋 응답 유실과 공급자별 전체 만료·제한 조합

공급자별 상세 조합을 확인하기 전에는 #78의 소셜 검증 항목 전체를 완료로 표시하지 않습니다.
빌드·로컬 확인·커밋·PR·CI·병합 상태도 각각 구분합니다.
