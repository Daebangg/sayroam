# 알림함 기본 API

알림함의 목록·개수 조회, 개별·전체 읽음 처리, 읽지 않음 변경과 개별 삭제를 제공합니다. 모든 요청은 로그인한 회원의 Bearer Access Token을 사용하며, 사용자 ID를 요청값으로 받지 않습니다.

## 개수 요약 조회

`GET /api/notifications/summary`

```json
{"totalCount": 12, "unreadCount": 3}
```

삭제되지 않은 본인 알림의 전체 개수와 미읽음 개수를 반환합니다. 목록 페이지 크기와 무관하며, 알림이 없으면 두 값 모두 0입니다. 알림 엔티티나 목록을 불러오지 않고 한 번의 DB 집계로 계산하며 조회만으로 읽음 처리하지 않습니다.

프론트는 알림 배지 등에서 이 응답을 사용할 수 있습니다. polling 주기·시작·중단과 탭 가시성 처리는 프론트 책임이며 백엔드에 주기 조회 스케줄러를 두지 않습니다.

## 목록 조회

`GET /api/notifications?beforeId=42&size=20`

- `beforeId`는 선택값입니다. 생략하면 최신 알림부터 조회하고, 다음 조회에는 이전 응답의 마지막 알림 ID를 전달합니다.
- `size`는 기본 20이며 1~100을 허용합니다. `beforeId`는 양수여야 합니다.
- `unreadOnly`는 기본 false입니다. `GET /api/notifications?unreadOnly=true`는 미읽음 알림만 같은 커서 방식으로 조회합니다. 필터를 바꾸면 `beforeId`를 생략해 처음부터 조회합니다.
- 본인의 삭제되지 않은 알림만 ID 내림차순으로 반환합니다. 조회만으로 읽음 처리하지 않습니다.
- 응답의 `notifications`에는 ID, 종류, 내용, 연결 대상 종류·ID, 읽음 여부와 생성 시각이 포함됩니다. 연결 대상이 없으면 종류와 ID는 모두 null입니다. 생성 시각은 UTC 기준입니다.
- 조건에 맞는 알림이 없으면 빈 배열을 반환합니다. 새 알림을 확인하려면 `beforeId`를 생략하고 다시 조회합니다.

## 읽음 상태 변경

`PATCH /api/notifications/{notificationId}`

```json
{"isRead": true}
```

`true`는 읽음, `false`는 읽지 않음으로 변경합니다. `isRead`는 필수이며 null을 허용하지 않습니다. 성공하면 본문 없이 204를 반환합니다. 이미 읽은 알림을 다시 읽음 처리하면 최초 읽음 시각을 유지합니다.

## 전체 읽음 처리

`PATCH /api/notifications`

```json
{"isRead": true}
```

본인의 미삭제·미읽음 알림만 한 번의 UPDATE로 읽음 처리합니다. 목록에서 현재 보이는 페이지에 한정하지 않습니다. 이미 읽은 알림의 최초 읽음 시각과 삭제한 알림의 상태는 유지하며 변경 시각도 함께 기록합니다. 반복 요청과 알림이 없는 경우 모두 본문 없이 204를 반환합니다. `isRead`는 필수이고 true만 허용합니다. false나 null은 400이며 전체 읽지 않음 기능은 제공하지 않습니다.

이후 새로 도착한 알림은 미읽음으로 남습니다. 요청 직후 새 알림이나 다른 기기 동작이 있을 수 있으므로 클라이언트는 완료 후 요약과 현재 필터의 첫 페이지를 재조회합니다.

## 삭제

`DELETE /api/notifications/{notificationId}`

삭제 시각을 기록해 알림함에서 숨기며 연결된 원래 데이터는 삭제하지 않습니다. 성공과 반복 삭제는 모두 204를 반환하고 최초 삭제 시각을 유지합니다.

## 오류와 검증

- 인증되지 않은 요청은 401, 잘못된 조회 조건·본문·ID 형식은 400입니다.
- 없는 알림과 다른 회원의 알림은 모두 404 `NOTIFICATION_NOT_FOUND`로 응답합니다.
- 삭제한 알림의 읽음 상태 변경은 409 `NOTIFICATION_DELETED`로 응답합니다.
- API 통합 테스트는 실제 인증 필터와 임시 MySQL·Redis를 사용해 조회 범위, 페이지 처리, 상태 변경, 반복 삭제와 오류를 확인합니다.

## 회원가입 축하 알림

이메일 가입과 소셜 신규 가입은 `AccountWriteService`에서 회원·로그인 수단을 먼저 커밋한 뒤, 별도 `REQUIRES_NEW` 트랜잭션에서 공용 `NotificationService.create`를 호출합니다. 알림 저장이 실패하면 해당 알림 트랜잭션만 롤백하고 실패 로그를 남깁니다. 이미 커밋한 회원과 로그인 수단은 유지하며 가입은 성공으로 응답합니다. 소비한 가입 증명·티켓을 복원하지 않는 기존 인증 정책은 유지합니다.

- 종류는 `WELCOME`이며 기본 안내 문구는 영어 `Welcome to SayRoam! Your next adventure starts here.`로 저장합니다.
- 사건 키는 `account-signup:<회원 ID>`이며 연결 대상 종류와 ID는 모두 null입니다. 프론트는 내용을 표시하고 페이지 이동 버튼을 만들지 않습니다. 관련 화면이 있는 다른 알림은 기존 `targetType`·`targetId`로 이동 대상을 결정합니다.
- 신규 가입 커밋 후 한 번 저장을 시도하며, 저장에 성공한 알림은 최초 로그인 후 REST 조회에서 확인할 수 있습니다. 기존 회원 로그인·소셜 계정 연결에서는 생성하지 않습니다. 기존 회원에게 소급 생성하지 않습니다.
- 가입 증명·티켓 재사용은 인증 흐름에서 거부하며 같은 사건의 중복 저장은 기존 수신자·사건 UNIQUE 제약으로 막습니다. 읽음·삭제 후 재로그인해도 새 알림으로 만들지 않습니다. 공용 생성 메서드가 중복 저장을 성공으로 간주하는 기능은 추가하지 않습니다.
- 소셜 가입 커밋 후 토큰 발급이 실패해도 이미 저장된 회원과 저장에 성공한 축하 알림은 남습니다. 이후 정상 로그인으로 확인할 수 있습니다.
- 알림 저장은 동기로 한 번 시도합니다. 자동 재시도·실패 작업 저장은 제공하지 않으므로 저장 실패나 회원 커밋 직후 프로세스 종료 시 축하 알림이 누락될 수 있습니다. 해당 재처리 보장은 후속 범위입니다.

## REST 재조회와 프론트 연동

요약은 배지 확인에, 목록은 알림함을 열거나 새로 고칠 때 사용합니다. 재접속·다른 기기에서는 DB에 저장된 최신 상태를 REST로 다시 조회하며, 새 알림 확인에는 커서를 생략합니다. 상태 변경 후에는 요약과 목록을 재조회합니다. 이 요청들은 알림 저장·읽음·삭제 상태를 계정 기준으로 공유합니다.

조회와 변경 모두 공통 Bearer 인증을 사용합니다. 401의 토큰 갱신은 프론트의 공통 인증 기반을 따르고, 400은 입력 수정, 404·409는 목록 재조회로 처리합니다. 네트워크 단절이나 5xx가 발생하면 서버 상태를 추정해 덮어쓰지 않습니다. 변경 응답을 받지 못한 경우 먼저 재조회해 반영 여부를 확인하며 변경 요청을 자동 반복하지 않습니다. polling의 주기·탭 가시성·중단·계정 변경 시 캐시 정리는 #164에서 구성합니다.

알림 생성용 공개 POST API는 제공하지 않습니다. 여행·매칭 등 다른 발생 조건 연결과 프론트 알림함 화면은 후속 범위입니다. 우선 REST API를 사용하며 SSE는 후속 검토 대상으로 둡니다.
