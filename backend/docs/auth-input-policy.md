# 로그인 제한과 인증 입력 정책 (#85)

## 실패 횟수와 차단

비밀번호 로그인은 정규화한 이메일과 서버가 확인한 원격 IP를 **각각** 집계합니다.
이메일은 첫 실패부터 300초 동안 5회 실패하면, 다섯 번째 실패 시점부터 300초 차단합니다.
IP는 여러 이메일에 걸쳐 첫 실패부터 300초 동안 100회 실패하면, 백 번째 실패부터 300초 차단합니다.
일반적인 첫 네 번의 이메일 실패는 401 `INVALID_CREDENTIALS`, 이메일 또는 IP가 임계값에 도달하면
429 `LOGIN_RATE_LIMITED`입니다. 아직 어느 기준으로도 차단되지 않았다면 다섯 번째 요청의
올바른 비밀번호는 로그인할 수 있습니다. IP 100회는 운영 초기값이며 트래픽에 맞춰 조정합니다.

이메일은 여러 IP에서도 같은 기준을 적용하고, IP는 여러 이메일에서도 같은 기준을 적용합니다.
요청의 임의 `X-Forwarded-For` 값은 사용하지 않습니다. 현재 배포에서 `getRemoteAddr()`가 기준이며,
프록시를 추가하면 신뢰할 프록시의 주소 전달 설정을 함께 검토해야 합니다. 공유 IP의 다른 사용자도
영향받을 수 있습니다. 계정 미존재·비밀번호 없는 소셜 계정·탈퇴·미인증도 같은 실패로 집계합니다.

차단 중 요청은 횟수와 만료를 늘리지 않습니다. 만료 후 새 구간으로 시작합니다. 성공하면 이메일
실패 이력만 지웁니다. IP 이력은 원래 구간 만료까지 유지해, 공격자가 자기 계정 로그인으로
IP 제한을 초기화할 수 없게 합니다. 기존 로그인 세션을 폐기하거나 비밀번호 재설정을 막지는 않습니다.

Redis Lua가 시간 조회·확인·증가·차단·TTL을 원자적으로 처리합니다. 비밀번호 검증 전과 결과 확정 시
차단 상태를 확인해, 다른 요청이 먼저 차단을 확정하면 이미 진행 중이던 검증도 토큰을 발급하지 않습니다.
다중 서버는 같은 Redis를 사용합니다. 두 키는 `{login-attempts}` 해시 태그로 같은 슬롯에 둡니다.
IP는 `ip-wide` 버킷을 사용합니다. 이전 5회 정책의 `ip` 버킷은 새 집계에 사용하지 않고 기존 TTL로
만료시켜 과거 차단이 새 정책에 남지 않게 합니다. 이메일 버킷과 차단은 유지합니다.
키에는 이메일·IP 원문 대신 SHA-256을 사용하며 역추정 불가능한 익명화를 의미하지는 않습니다.

Redis 장애는 503 `LOGIN_ATTEMPTS_UNAVAILABLE`로 종료하고 토큰·쿠키를 발급하지 않습니다.
메모리 저장소 우회나 자동 재전송은 없습니다.

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| `app.auth.login-attempts.max-failures` | 5 | 이메일별 차단을 시작하는 실패 횟수 |
| `app.auth.login-attempts.ip-max-failures` | 100 | IP별 차단을 시작하는 실패 횟수 |
| `app.auth.login-attempts.window-seconds` | 300 | 첫 실패부터의 관찰 구간 |
| `app.auth.login-attempts.block-seconds` | 300 | 임계 실패부터의 차단 시간 |

## HTTP와 화면

429는 `application/problem+json`, `Cache-Control: no-store`이며 아래 필드를 필수로 제공합니다.
`Retry-After` 헤더와 `retryAfterSeconds`는 남은 시간을 올림한 동일한 양의 정수 초입니다.
계정 존재 여부는 공개하지 않습니다. 401 `INVALID_CREDENTIALS`에는 필수 `remainingAttempts`를
제공합니다. 해당 이메일의 남은 횟수이며 기본 정책에서 4·3·2·1로 줄어듭니다. IP 집계 수치는 공개하지 않습니다.
이메일 로그인 성공 후 같은 IP에서 다시 실패해도 해당 이메일은 4회가 남습니다.
미가입 이메일도 같은 방식으로 집계하고 공개합니다. 차단된 429는 남은 횟수 대신 대기 시간을 제공합니다.

```json
{
  "status": 429,
  "code": "LOGIN_RATE_LIMITED",
  "retryAfterSeconds": 300
}
```

OpenAPI `LoginRateLimitedProblem`과 `LoginRateLimited` 응답에 필수 필드·헤더를 명시합니다.
프론트는 이 시간을 카운트다운으로 표시하고 대기 중 재요청을 막습니다. 만료 후 사용자가 직접
재시도합니다. 새로고침으로 프론트 상태가 초기화돼도 Redis 차단은 유지됩니다.

## 공통 입력

| 입력 | 정책과 적용 위치 |
| --- | --- |
| 신규 비밀번호 | 8~24자, ASCII 대문자·숫자 각 1개 이상, Unicode 문장부호/기호 특수문자 1개 이상, 공백·제어·숨김 문자 금지. 회원가입·변경·재설정 공통 |
| 로그인 비밀번호 | 기존 8~128자 유지. 새 조합 조건을 강제하지 않고 원문 그대로 해시 검증. 로그인 후 본인 확인을 거쳐 새 조건으로 변경 가능 |
| 닉네임 | 앞뒤 공백 제거 후 1~50 UTF-16 코드 단위. 내부 공백·한글·이모지 허용. Unicode C 범주·줄/문단 구분자 금지. 일반/소셜 가입·프로필 변경 공통 |
| 이메일 | 앞뒤 공백 제거·전체 소문자 비교. ASCII dot-atom 로컬 부분 64자 이하, 전체 254자 이하, 도메인 각 레이블 63자 이하, 점으로 구분한 도메인 필요. 가입·인증·로그인·재설정·소셜 공급자 이메일 공통 |

이메일은 인용 로컬 부분·연속 점·원문 국제화 도메인을 받지 않으며 punycode 도메인은 허용합니다.
Gmail 점·플러스 주소를 합치지 않습니다. 소셜 공급자의 부적합 이메일은 신뢰하지 않고 수동 가입
정보 보완 경로로 보냅니다. 길이는 Java·JavaScript의 문자열 길이 기준이며 화면·서버·명세를 맞춥니다.
비밀번호에는 공백 제거·대소문자 변환을 적용하지 않습니다.

회원가입 코드 요청은 발송 전 DB에서 이메일 점유를 확인해 기존 이메일이면
409 `EMAIL_ALREADY_REGISTERED`로 종료합니다. 소셜 계정·DB에 남아 있는 탈퇴 이메일도 포함하며,
Redis 예약·발송 제한 소비·SMTP 전송을 하지 않습니다. 발송 이후의 경쟁은 최종 DB UNIQUE 검증이
계속 담당합니다. 재설정 API의 계정 존재 여부 비공개 계약은 유지합니다.

## 로그인 상태 유지

`LoginRequest.rememberMe`는 선택 입력이며 생략·null은 기존 동작인 true입니다.
true는 남은 절대 TTL을 Max-Age로 쓰는 영속 Refresh 쿠키, false는 Max-Age 없는 브라우저 세션
쿠키를 발급합니다. 브라우저가 세션 복원으로 쿠키를 복구할 수 있으므로 창 닫기가 서버 세션의
즉시 폐기를 보장하지는 않습니다. Redis 절대 만료는 양쪽 모두 적용합니다.

선택 값은 Redis 로그인 메타데이터에 저장하고 갱신 교체 시에도 유지합니다. 기존 세션에 필드가
없으면 true로 읽습니다. 별도 추적 쿠키·HttpSession·DB 테이블은 추가하지 않습니다.

## 검증

격리된 MySQL·Redis 통합 테스트에서 임계 실패·만료·성공·다중 IP/이메일·이메일 32개·IP 128개 동시 요청·
Redis 중단·동시 가입 충돌·쿠키 선택과 갱신·기존 128자 비밀번호 로그인 및 변경을 확인합니다.
서버 OpenAPI를 내보내 저장 계약·생성 타입을 갱신하며, 프론트는 대기 중 POST 차단과 만료 후
수동 재시도를 검증합니다. 실제 SMTP 수신은 이 제한 정책의 검증에 포함하지 않습니다.
