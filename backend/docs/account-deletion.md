# 회원 탈퇴·계정 정리 (#30 6단계)

로그인한 회원이 `ACCOUNT_DELETION` 이메일 본인 확인 후 자신의 계정을 탈퇴합니다.
현재 회원의 프로필·로그인 수단·개인 설정을 정리하면서 채팅·정산 등 공유 기록의 회원 ID 참조는 보존합니다.
성별·출생연도 설정·변경은 별도 #42의 후속 작업이며 가입 필수 정보는 이메일·비밀번호·닉네임을 유지합니다.

## API와 브라우저 흐름

1. `GET /api/auth/csrf`로 CSRF 쿠키를 준비합니다.
2. Bearer 인증과 CSRF 쿠키·헤더를 사용해 `POST /api/auth/account-verifications`에
   `{"purpose":"ACCOUNT_DELETION"}`을 보냅니다.
3. 같은 목적·요청 ID로 `/api/auth/account-verifications/verify`에서 코드를 확인하고 `accountProof`를 받습니다.
4. 아래 요청으로 탈퇴를 실행합니다. 회원 ID·이메일·목적은 요청에서 받지 않습니다.

```http
POST /api/auth/account-deletion
Authorization: Bearer <accessToken>
Content-Type: application/json
X-XSRF-TOKEN: <XSRF-TOKEN 쿠키 원문>
Cookie: XSRF-TOKEN=<같은 원문>
```

```json
{"accountProof":"<ACCOUNT_DELETION 확인에서 받은 43자 증명>"}
```

가입용 `signupProof`·비밀번호 변경용 증명·다른 회원/이메일/인증 버전의 증명은 사용할 수 없습니다.
별도의 비밀번호 입력은 받지 않습니다. 비밀번호 유무와 무관하게 현재 인증된 대표 이메일의 본인 확인이 필요합니다.
소셜 계정의 이메일이 없거나 인증되지 않았다면 #31의 이메일 보완 인증 흐름을 먼저 거쳐야 합니다.

성공은 **204 No Content**, `Cache-Control: no-store`와 현재 Refresh 쿠키 만료입니다.
발급과 같은 `Path=/api/auth`, HttpOnly·SameSite=Strict·Secure 설정을 사용합니다.
XSRF-TOKEN 쿠키는 유지하며 새로운 로그인 토큰이나 탈퇴 계정의 개인정보를 반환하지 않습니다.

프론트는 Access Token·회원 정보·본인 확인 증명을 메모리에서 지우고 자동 갱신을 중단합니다.
같은 쿠키를 사용하는 탭에 로그인 종료를 알리며 진행 중인 로그인·갱신 결과로 상태를 되살리지 않습니다.
로그인/갱신/민감 작업의 동시 실행을 조정하고, 네트워크 오류나 503을 탈퇴 성공으로 표시하지 않습니다.
현재 작업은 백엔드와 연동 계약까지이며 프론트 화면 구현을 포함하지 않습니다.

## 실행 흐름과 트랜잭션

1. Security 필터가 Bearer 서명·만료·활성 회원·인증 버전과 auth 경로의 CSRF를 검사합니다.
2. `AccountDeletionController`가 principal의 회원 ID·인증 버전과 검증한 본문을 서비스로 전달합니다.
3. `AccountDeletionService`가 `AccountVerificationService.consumeProof`에 서버 상수
   `ACCOUNT_DELETION`을 전달합니다. Redis Lua가 현재 회원·이메일·목적·인증 버전·TTL·다이제스트를 확인해 한 번만 소비합니다.
4. `JpaAccountDeletion`이 새 DB 트랜잭션에서 회원 행에 쓰기 잠금을 잡고
   활성/이메일 인증 상태·현재 이메일·예상 인증 버전을 다시 확인합니다.
5. `AccountDeletionCleanup` 포트로 Application의 정리 작업을 호출해 로그인 수단·개인 여행 성향·수신 알림을 삭제하고,
   `User.withdraw`로 프로필을 익명화하며
   UTC 탈퇴 시각과 증가한 인증 버전을 저장합니다. **모두 같은 MySQL 트랜잭션으로 커밋**합니다.
6. 커밋 확인 후에만 204와 Refresh 쿠키 만료를 반환합니다. 커밋 뒤 Redis·SMTP·외부 공급자 호출은 없습니다.

Application은 본인 확인 서비스와 삭제 포트에 의존하며 JPA·Redis·HTTP 타입을 직접 참조하지 않습니다.
Infrastructure가 DB 정리를 담당하고 Presentation이 principal·본문·쿠키·상태 코드를 처리합니다.
기존 V1/V2 컬럼을 사용하며 이번 작업에 새 마이그레이션은 없습니다.

정리 범위·순서는 `AccountDeletionCleanupService`가 회원·여행 성향·알림 소유의 포트로 정의합니다.
각 도메인의 JPA 어댑터만 자기 데이터의 삭제 쿼리를 알고, `JpaAccountDeletion`은 다른 도메인의 쿼리를 직접 실행하지 않습니다.
세 정리 어댑터는 `MANDATORY` 전파를 사용해 현재 탈퇴 트랜잭션에만 참여합니다. 트랜잭션이 없으면 실행을 거절하며,
별도 트랜잭션으로 일부 데이터만 먼저 커밋하지 않습니다. 실패는 바깥 탈퇴 트랜잭션까지 전파해 함께 롤백합니다.

## 정리·보존 범위

| 대상 | 탈퇴 커밋 시 처리 |
| --- | --- |
| `users` | 행·회원 ID·생성/수정 시각 유지, `deletedAt` 기록, `authVersion` 증가 |
| 대표 이메일·이메일 인증 시각·프로필 이미지 URL·성별·출생연도 | NULL로 정리 |
| 닉네임·권한 | `탈퇴한 회원`·USER로 변경 |
| `user_credential` | 해당 회원의 비밀번호 해시·변경 시각을 포함한 자격 정보 삭제 |
| `user_social_account` | 해당 회원의 공급자 ID·공급자 이메일을 포함한 로컬 연결 삭제 |
| `user_travel_style` | 해당 회원의 개인 성향 응답 삭제. 공용 질문 항목은 유지 |
| `notification` | 해당 회원이 수신자인 알림 삭제. 다른 회원의 알림은 유지 |
| 방·방 멤버·초대·여행·장소·동행 글/요청·채팅·지출·분담 | 공유 이력과 참조를 보존하며 회원 ID를 새 회원에게 옮기지 않음 |

공유 기록에서 회원의 현재 프로필을 조회할 때는 보존된 회원 행의 `탈퇴한 회원` 표시와 빈 프로필을 사용합니다.
이미 전송한 메시지 본문·동행 글/요청 문구·다른 회원의 알림 문구 같은 공유 콘텐츠는 이번 계정 프로필 정리에서 다시 쓰지 않습니다.
실제 해당 기록 조회 화면은 각 기능 구현 시 이 표시 기준을 따라야 하며 이번 작업에서 화면을 새로 만들지는 않습니다.

방 자동 나가기·방장 승계·동행 글 종료 같은 업무 상태 변경이나 지출 이력 삭제는 이번 인증·계정 정리 범위에 포함하지 않습니다.
각 업무 기능은 참여자/대상의 활성 회원 상태도 확인해야 하며, 단순히 보존된 멤버/요청 행이 있다는 이유로 탈퇴 계정의 접근을 허용하면 안 됩니다.
향후 프로필 저장·소셜 연결 같은 회원 소유 데이터 쓰기도 회원 잠금 및 활성 상태 확인을 통해
탈퇴와 경합할 때 탈퇴 계정에 데이터를 다시 생성하지 않도록 구성해야 합니다.

현재 프로필 이미지는 URL 필드만 있으므로 외부 파일 저장소에서 객체를 삭제하는 기능은 없습니다.
소셜 연결 정리는 로컬 연결 삭제이며 공급자 계정 자체를 삭제하지 않습니다.
공급자 동의/외부 토큰 철회는 #31의 실제 공급자 연동 시 별도로 처리해야 하며, 로컬 탈퇴 차단은 그 호출 결과에 의존하지 않습니다.

## 로그인 차단·재가입·재연결

- **이메일 로그인:** 자격 정보 삭제와 `deletedAt` 확인으로 기존 계정은 401 INVALID_CREDENTIALS입니다.
  없는 이메일과 잘못된 비밀번호처럼 동일한 공개 오류를 사용합니다.
- **Access Token:** 다음 인증의 활성 회원 조회에서 401입니다. 잔여 만료 시간이나 허용 시간 오차로 탈퇴 회원을 허용하지 않습니다.
- **Refresh Token:** 현재 활성 회원이 없으므로 401 REFRESH_TOKEN_INVALID와 쿠키 만료입니다.
- **본인 확인:** 삭제된 계정은 활성·인증된 대표 이메일이 없으므로 기존 코드/증명을 사용할 수 없습니다.
- **Redis:** 기존 Refresh·코드·증명·제한 키는 원래 TTL까지 남을 수 있지만 인증·갱신 권한은 없습니다.
  삭제 커밋 이후 Redis 키 일괄 삭제 성공을 기다리지 않으며 다른 회원의 키를 스캔·삭제하지 않습니다.

커밋 전에 이미 인증을 마친 일반 요청은 소급 취소하지 않습니다. 이전에 시작한 로그인·갱신 응답이
탈퇴 후 도착해도 그 토큰의 회원 ID는 이미 탈퇴 상태여서 다음 인증에 사용할 수 없습니다.
민감 작업은 DB 잠금 안에서 다시 확인하므로 비밀번호 변경·탈퇴 중 같은 버전에서는 한 작업만 커밋할 수 있습니다.

대표 이메일을 NULL로 비우므로 탈퇴 커밋 후 같은 이메일의 정상 이메일 인증·가입을 허용합니다.
재가입은 새 회원 ID·새 자격 정보이며 기존 행을 복구하거나 채팅·정산·방 멤버·여행 기록을 이어 붙이지 않습니다.
탈퇴 전 계정의 Access/Refresh/계정 관리 증명을 새 회원에게 사용할 수도 없습니다.

소셜 연결도 삭제해 공급자 식별자의 로컬 연결 제약을 해제합니다. #31은 공급자 인증을 새로 확인한 뒤
새 가입 또는 로그인한 활성 계정의 명시적 연결 흐름을 사용해야 합니다. 같은 이메일/공급자 ID라는 이유로
탈퇴 계정을 자동 복원하거나 새 회원과 과거 기록을 병합하지 않습니다. 실제 소셜 재연결 API는 #31에서 구현합니다.

## 실패·중복·동시 요청·응답 유실

| 상황 | 처리와 재시도 |
| --- | --- |
| 입력·CSRF·Bearer 실패, 잘못된 증명 바인딩 | DB 삭제 전에 거절. 정상 증명을 임의로 소비하거나 다른 계정을 변경하지 않음 |
| 사전 회원 조회 DB 장애 | 503 AUTHENTICATION_UNAVAILABLE. 이 요청의 증명 소비·삭제는 시작하지 않음 |
| Redis 증명 소비 결과 불확실 | 503 EMAIL_VERIFICATION_UNAVAILABLE. DB 삭제는 시작하지 않음. 증명은 이미 소비됐을 수 있으므로 활성 계정에서 새 본인 확인 필요 |
| 같은 증명의 중복 요청 | 한 요청만 소비. 나머지는 409 ACCOUNT_PROOF_ALREADY_USED 또는 현재 계정의 인증/활성 상태 오류 |
| 다른 증명·비밀번호 변경과 동시 탈퇴 | 회원 쓰기 잠금과 예상 버전/이메일/상태 검사로 충돌 거절. 소비한 증명은 복원하지 않음 |
| 소비 뒤 계정 상태 충돌 | 409 ACCOUNT_DELETION_CONFLICT. 계정이 여전히 활성인 경우만 재로그인·새 본인 확인으로 재시도 |
| DB 정리·잠금·연결·커밋 장애 | 503 ACCOUNT_DELETION_UNAVAILABLE. DB 변경은 한 트랜잭션이지만 커밋 확인이 불확실할 수 있음. Refresh 쿠키 만료 및 로컬 로그인 상태 정리, 자동 재전송 금지 |
| 204 응답 유실 | 탈퇴가 이미 끝났을 수 있음. 같은 요청을 자동 재전송하거나 자동 재가입하지 않음 |

서버는 증명 소비를 되돌리거나 성공 응답을 재생하지 않으며 자동 재시도하지 않습니다.
서비스에서 재시도하지 않는 것과 Redis 드라이버의 재연결/재전송 정책은 구분합니다.
삭제 트랜잭션이 롤백되면 DB 변경은 함께 롤백되지만 Redis에서 소비한 증명은 복원하지 않습니다.

이미 탈퇴한 회원은 Bearer 인증에 실패하므로 반복 탈퇴에 무조건 204를 주는 공개 경로를 만들지 않습니다.
네트워크 오류·503 이후 **로그인 실패나 401만으로 탈퇴 성공을 확정할 수는 없습니다.**
프론트는 완료 여부가 불확실함을 표시합니다. 다시 로그인할 수 있다면 새 본인 확인으로 재시도할 수 있고,
그렇지 않다면 원인을 확인해야 합니다. 공개 계정 존재 조회·탈퇴 결과 조회·탈퇴 복구 API는 제공하지 않습니다.

## 오류와 확인 범위

공통 `application/problem+json`, `code`, `Cache-Control: no-store` 형식을 사용합니다.

| HTTP | code |
| --- | --- |
| 400 | INVALID_INPUT, ACCOUNT_PROOF_INVALID 또는 Spring 요청 오류 |
| 401 | UNAUTHENTICATED, AUTHENTICATION_REVOKED. WWW-Authenticate: Bearer |
| 403 | INVALID_CSRF_TOKEN, ACCESS_DENIED, ACCOUNT_VERIFICATION_NOT_ALLOWED |
| 409 | ACCOUNT_PROOF_ALREADY_USED, ACCOUNT_DELETION_CONFLICT |
| 410 | ACCOUNT_PROOF_EXPIRED. 해당 회원/이메일/목적/버전의 증명이 없는 경우 포함 |
| 503 | AUTHENTICATION_UNAVAILABLE, EMAIL_VERIFICATION_UNAVAILABLE, ACCOUNT_DELETION_UNAVAILABLE |
| 500 | INTERNAL_SERVER_ERROR. 예상하지 못한 매핑·프로그래밍 오류 |

503 중 ACCOUNT_DELETION_UNAVAILABLE에서만 Refresh 쿠키를 만료시킵니다.
테스트 전용 MySQL·Redis를 사용하는 API 통합 검증을 추가했습니다.
실행 방법, 확인한 흐름과 남은 검증 범위는 [인증 테스트 안내](auth-testing.md)를 참고하세요.
