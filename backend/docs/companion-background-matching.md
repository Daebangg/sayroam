# 동행 모집의 백그라운드 후보 발견

관련 이슈: [#149](https://github.com/Daebangg/sayroam/issues/149), [#172](https://github.com/Daebangg/sayroam/issues/172)

모집 등록·수정·재개가 커밋되면 화면 접속과 무관하게 후보를 찾고 MySQL에 발견 이력을 저장합니다.
새 후보 조합을 처리하면 양쪽 회원의 알림을 함께 저장합니다. 프론트 화면·폴링·SSE·이메일 발송은 후속 범위입니다.

## 실행 시점과 날짜 기준

- 등록·수정·종료 후 재개 시 모집 변경과 `companion_matching_job` 생성을 같은 트랜잭션으로 저장합니다. 롤백되면 작업도 남지 않습니다.
- 이미 활성 상태인 모집에 ACTIVE를 반복 요청하거나 모집을 종료할 때는 새 작업을 만들지 않습니다.
- DB 커밋 성공 후 `CompanionMatchingRequested` 이벤트를 받으면 전용 작업 스레드를 즉시 깨웁니다. 커밋 전과 롤백 시에는 실행 신호를 보내지 않습니다.
- 이벤트 리스너는 실행 신호만 제출합니다. 실제 DB 선점·후보 처리 트랜잭션은 별도 스레드에서 시작하므로 HTTP 요청은 후보 계산을 기다리지 않습니다.
- 서버 시작 시 미처리 작업을 확인하고, 기본 30초 간격의 복구 실행으로 이벤트 누락·실패·선점 만료 작업을 회수합니다. 완료된 모집을 주기적으로 다시 계산하지 않습니다.
- 다른 회원이 모집을 등록·수정·재개할 때 기존 모집과의 조합도 확인하므로 기존 등록자 쪽 후보 발견도 가능합니다.
- 나이와 기간 만료는 각 처리 배치의 `Asia/Seoul` 당일을 기준으로 합니다. 겹치는 기간의 종료일 당일까지 포함하고, 지난 조합은 저장하지 않습니다.
- 전체 모집의 매일 재계산, 프로필·생일·스타일 변경에 따른 자동 재계산은 이번 범위에 포함하지 않습니다.

## 후보 선정과 저장

화면 조회와 공통으로 같은 여행지·하루 이상 겹치는 기간·양쪽 희망 나이·성별·프로필 미입력 기준을 사용합니다.
탈퇴한 회원, 종료한 모집과 비활성 여행지는 제외합니다. 스타일 점수와 화면용 제목 검색은 자동 발견의 필수 조건으로 쓰지 않습니다.

화면은 회원별 대표 모집 한 건을 제공하지만, 발견 이력은 이슈 기준에 따라 조건에 맞는 **모집 조합별**로 저장합니다.
작은 모집 ID를 `first_search_id`, 큰 모집 ID를 `second_search_id`로 정규화하고 UNIQUE 제약으로 양방향·재처리 중복을 막습니다.
동일 회원의 모집끼리는 발견하지 않습니다. 발견 이력은 모집 조합별로 유지하고, 알림은 탐색 작업·내 모집별로 묶습니다. 한 번의 탐색에서 여러 후보·같은 상대의 여러 모집을 발견해도 내 모집의 안내 알림은 한 건입니다.

`companion_discovery`에는 양쪽 모집 ID·조건 버전·겹치는 기간·최초 생성 시각·마지막 매칭 확인 시각을 저장합니다.
다시 발견해도 최초 생성 시각은 유지합니다. 양쪽 버전이 모두 기존 기록 이상인 결과만 최신 정보에 반영하여 늦게 처리된 이전 결과가 덮어쓰지 못하게 합니다.

이 테이블은 **발견 이력**이며 현재 유효한 후보 목록 캐시가 아닙니다. 이후 모집 종료·조건 변경·기간 경과·회원 탈퇴가 발생해도 이력은 남습니다.
알림 저장 전 상대 모집을 잠가 조회 때의 버전과 현재 상태·기간을 확인하고 양쪽 회원을 잠가 탈퇴 여부와 상호 프로필 조건을 다시 검증합니다. 여행지 활성 여부도 재확인합니다. 검증 중 변경된 상대는 이번 배치에서 건너뛰고, 상대 변경으로 등록된 새 작업에서 다시 확인합니다. 프로필 변경 자체가 재탐색 작업을 생성하지는 않습니다.
현재 공개 후보 API는 계속 실시간 조회를 사용하므로 알림을 확인할 때도 과거 이력을 현재 후보로 취급하지 않습니다.

## 선점·분할·재시도

- `FOR UPDATE SKIP LOCKED`로 작업 한 건을 선점하고 토큰을 저장합니다. 여러 서버가 같은 유효 선점을 공유하지 않습니다.
- `available_at`은 PENDING/RETRY 상태의 다음 실행 시각, PROCESSING 상태의 선점 만료 시각입니다. 종료 상태에서는 NULL로 큐 인덱스에서 제외합니다.
- 선점 유효 시간은 5분입니다. 서버 중단으로 PROCESSING이 남으면 만료 후 다른 실행이 새 토큰으로 회수합니다. 이전 토큰의 완료·재시도 요청은 무시합니다.
- 처리 트랜잭션은 작업 행과 원본 모집을 잠그고 최신 버전을 확인합니다. 이전 버전 작업과 종료·만료된 원본은 SKIPPED로 끝냅니다.
- 후보별로 상대 모집·양쪽 회원을 잠그고 재검증한 뒤 발견과 알림을 기록합니다. 양방향 작업이나 회원 변경과의 잠금 경합으로 교착이 발생하면 배치 전체를 롤백하고 기존 재시도 경로로 처리합니다.
- 모집 ID 커서로 최대 100개 조합씩 처리합니다. 이어서 처리할 때도 원본의 버전을 다시 확인합니다. 한 번의 실행은 최대 10배치이며, 더 처리할 작업이 있으면 복구 주기를 기다리지 않고 다음 실행을 제출합니다.
- 여러 이벤트가 몰려도 메모리 실행 큐에는 신호 한 건만 유지합니다. 실행 종료 직전 도착한 신호도 다음 실행으로 넘겨 놓치지 않습니다. 실제 작업의 원본은 DB이며 이벤트는 큐를 깨우는 신호입니다.
- 전용 `ThreadPoolTaskExecutor`는 작업 스레드 하나·대기 실행 한 건을 사용합니다. 복구 타이머는 별도 `ThreadPoolTaskScheduler`에서 실행 신호만 제출하며, 둘 다 채팅 스케줄러와 분리됩니다.
- 실행 제출이 거부되어도 커밋된 DB 작업은 유지하며 다음 이벤트·시작 시 확인·복구 실행에서 처리합니다.
- 배치의 발견 기록·양쪽 알림·커서·완료 상태를 같은 트랜잭션으로 저장합니다. 한쪽 알림 저장 실패를 포함해 실패하면 배치 전체가 롤백됩니다.
- 실패하면 다음 실행 가능 시각을 5·10·20·40·80·160·300초 뒤로 저장하며 이후에는 300초를 유지합니다. 해당 시각 이후 다른 이벤트나 복구 실행에서 다시 가져오므로 복구 주기만큼 추가 지연될 수 있습니다. 재시도 저장도 실패하면 선점 만료 후 회수합니다.
- 양방향 작업의 FK·발견 행 잠금 경합에서 발생하는 DB 교착도 같은 재시도 경로로 처리합니다.

## 최초 탐색 상태와 후보 조회

`GET /api/companion-searches/{searchId}/matching-status`는 인증된 회원 본인의 모집만 조회합니다. 다른 회원의 모집과 없는 모집은 모두 404 `COMPANION_SEARCH_NOT_FOUND`이며 인증이 없으면 401입니다. 조회는 작업을 생성하거나 재실행하지 않습니다.

```json
{"searchId": 101, "matchingRevision": 3, "status": "PROCESSING"}
```

- `matchingRevision`은 현재 모집의 조건 버전입니다. 과거 버전의 성공을 현재 탐색 완료로 반환하지 않습니다.
- `PENDING`은 대기·다음 배치 대기, `PROCESSING`은 처리 중, `RETRY`는 실패 후 재시도 대기, `SUCCEEDED`는 현재 조건의 최초 탐색 완료입니다.
- `SUCCEEDED`는 후보 존재나 동행 확정을 뜻하지 않습니다. 후보가 0명이어도 완료되며, 이후 새 모집에서 후보를 발견해도 완료된 최초 작업 상태는 그대로입니다.
- `SKIPPED`는 종료·기간 만료·기존 자유 입력 지역 등 탐색할 수 없는 모집 또는 건너뛴 현재 작업입니다.
- `NOT_REQUESTED`는 탐색 가능한 모집이지만 현재 조건의 작업이 없는 상태입니다. 최초 탐색 중으로 표시하지 않으며 조회로 작업을 만들지 않습니다.
- 생성·수정·상태 변경 응답과 내 모집 목록에도 `matchingRevision`·`matchingStatus`를 추가합니다. 기존 응답의 추가 메타데이터는 호환성을 위해 명세의 선택 필드이며 서버는 항상 제공합니다. 전용 상태 응답의 세 필드는 필수입니다. 목록은 모집별 쿼리를 반복하지 않고 최신 작업을 일괄 조회합니다.
- 최초 탐색 대기 후에는 기존 `GET /api/companion-searches/{searchId}/candidates`로 최신 후보를 조회합니다. 여러 후보의 페이지 처리·회원별 대표 모집·공개 프로필·여행 스타일 비교 계약은 유지합니다.

프론트 후속 연동 시 생성·수정·재개 및 화면 복귀에서 상태를 조회하고, 현재 조건의 최초 탐색 중에만 짧게 재조회합니다. 완료·종료·이탈·숨김 탭·오프라인에서는 빠른 재조회를 중단합니다. 지연·재시도·통신 실패를 후보 없음으로 표시하지 않습니다. 후보 화면의 갱신과 알림함의 갱신은 각 화면에서 별도로 관리하며 서버에 프론트 폴링 타이머를 추가하지 않습니다.

## 발견 알림

- 유형은 `COMPANION_MATCH_FOUND`, 대상은 `COMPANION_SEARCH`, `targetId`는 **각 수신자 본인의 모집 ID**입니다. 알림에는 상대의 비공개 나이·성별이나 회원 식별자를 포함하지 않습니다.
- 사건 키는 `companion-matching-job:<작업 ID>:search:<수신자 모집 ID>`입니다. 100건 초과 배치와 재시도에서도 같은 키를 사용하므로 한 작업에서 내 모집의 알림은 한 번만 생성합니다. 처리 도중 읽거나 삭제해도 같은 작업에서 다시 만들지 않습니다.
- 배치의 신규 발견을 저장하면서 대상 모집 ID를 모아 중복 제거한 뒤 모집별로 알림 서비스를 한 번 호출합니다. 같은 회원의 서로 다른 모집은 각각 안내하며, 배치 간 중복은 위 사건 키로 차단합니다. 발견 이력은 모든 유효 조합을 계속 저장합니다.
- 양쪽 모집을 잠근 상태에서 최초 발견인지 확인합니다. 이미 알려진 조합은 이력만 갱신하며 반대 방향 탐색·조건 수정·종료 후 재개로 재발견해도 알림을 다시 만들지 않습니다.
- 이전 작업의 미읽음 알림이 남아 있어도 다른 작업에서 새 후보 조합을 발견하면 그 작업의 안내를 별도로 생성합니다. 이전 알림의 읽음 여부는 새 탐색 결과의 안내 여부를 결정하지 않습니다.
- 같은 작업은 배치 사이에 알림을 읽거나 삭제해도 저장된 사건 키로 추가 생성을 차단합니다. 과거 알림의 내용·읽음·삭제 상태는 변경하지 않습니다.
- 읽음·삭제 후 재처리해도 최초 내용·대상·읽음 시각·삭제 시각·생성 시각을 유지합니다. 기본 안내 문구는 가입 축하 알림과 동일하게 영어로 저장합니다. 제목이 없으면 `New travel companion candidates were found for your recruitment.`, 있으면 `New travel companion candidates were found for "<모집 제목>".`이며 사용자 입력 제목은 원문을 유지합니다. 생성 시점의 문구를 스냅샷으로 보존합니다.
- 알림 저장은 발견과 같은 트랜잭션입니다. 한쪽 저장 실패나 프로세스 중단 시 미커밋 배치는 롤백되며 DB 작업의 재시도·선점 만료 복구에서 다시 처리합니다. 커밋 후에는 알림함 REST 조회로 확인합니다.
- 후보가 없으면 발견 알림을 만들지 않습니다. 과거 발견 이력에 대한 일괄 소급 생성은 하지 않으며 배포 이후 처음 발견한 유효 조합만 묶음 알림의 발생 대상으로 삼습니다.
- 프론트는 대상 모집의 현재 후보를 다시 조회해야 합니다. 과거 알림이 있어도 상대 모집 종료·조건 변경·탈퇴로 후보가 사라질 수 있습니다. 알림 읽음과 후보 확인은 별도 의미입니다.

### 프론트 연동과 배포 순서

#172에서 도입한 가입·발견 알림은 `WELCOME`·`COMPANION_MATCH_FOUND`이며 발견 알림의 대상은 `COMPANION_SEARCH`입니다. 이후 추가된 요청·수락·거절 알림 유형과 대상은 [롬 메이트 요청](companion-requests.md)을 참고하세요.

실행 서버에서 추출한 명세는 `backend/build/openapi/openapi.json`에 생성합니다. 프론트는 해당 명세로 `frontend/contracts/openapi.json`과 생성 타입을 갱신하고 알림의 수신 검증·번역·이동 대상을 함께 연결합니다. 새 유형을 거부하는 이전 화면이 알림 목록 전체를 오류 처리할 수 있으므로, 해당 유형을 처리하는 프론트를 먼저 또는 백엔드와 함께 배포합니다.

## 설정과 배포

```properties
app.companion.matching.enabled=true
app.companion.matching.recovery-delay-ms=30000
```

`enabled=false`이면 이벤트 작업자와 복구 타이머를 끄고 모집 변경 작업은 계속 DB에 쌓습니다. 다시 활성화해 앱을 시작하면 미처리 작업을 이어서 처리합니다.
이벤트는 빠른 실행을 위한 메모리 신호이므로 유실될 수 있습니다. DB 작업 저장과 시작 시 확인·복구 타이머가 누락을 보완합니다.
`recovery-delay-ms`는 복구 신호 제출이 끝난 뒤 다음 신호를 보내기까지의 지연이며 최초 복구도 같은 시간 뒤 실행합니다. 기존 `poll-delay-ms` 설정은 사용하지 않습니다.
작업이 밀리면 이벤트를 받아도 실제 후보 발견까지 대기 시간이 생길 수 있습니다.

앱 시작 전에 [마이그레이션 안내](../gradle/README.md)에 따라 V20까지 적용합니다. V15는 새 테이블 두 개와 모집 버전·조회 인덱스를 추가하고,
기존 회원의 활성·미만료 모집 중 활성 기준 여행지가 있는 모집에 최초 작업을 만듭니다. 자유 입력 지역만 남은 기존 모집은 제외합니다. V20은 알림 유형·대상 ENUM을 확장하고 모집별 최신 작업 조회 인덱스를 추가합니다.
작업·발견 행은 모집에 FK로 연결되며 모집을 물리 삭제하면 함께 삭제됩니다. 계정 탈퇴는 기존 정책대로 회원 행을 보존하므로 처리·소비 시 탈퇴 여부를 확인합니다.

## 검증

`CompanionMatchingIntegrationTest`는 임시 MySQL·Redis에서 커밋·롤백, 상호 조건, 조합 중복, 최신 버전,
100건 초과 분할, 알림 저장 실패 시 배치 롤백·재시도, 중단 작업 회수·오래된 토큰 차단, 동시 선점과 양쪽 알림 생성, 여러 후보·100건 초과 배치·양방향 작업의 묶음 알림, 재검증과 읽음·삭제 후 기존 후보 중복 방지 및 새 후보 재안내를 확인합니다.
`CompanionSearchApiIntegrationTest`는 본인 조회 범위, 작업 상태 전이, 조건 변경·종료·재개, 빈 결과 완료와 작업 없음 상태를 확인합니다.
`SayroamApplicationTests`는 빈 DB와 기존 버전에서 V15 적용·최초 작업 생성·스키마 매핑을 확인합니다.
`CompanionMatchingEventIntegrationTest`는 복구 주기를 한 시간으로 두고, 커밋 이후 이벤트만으로 결과가 저장되는지 확인합니다.
커밋 전·롤백 시 리스너 미실행과 이벤트 누락 작업의 복구 진입점도 확인합니다.
`CompanionMatchingWorkerTest`는 신호 병합, 10배치 이후 즉시 연속 실행, 종료 시점 신호 보존, 실행 제출 거부 후 복구를 확인합니다.
나머지 통합 테스트에서는 자동 실행을 끄고 작업자를 직접 호출합니다. 모든 검증은 개발 DB와 SMTP를 사용하지 않습니다.
