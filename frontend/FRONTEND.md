# 프론트엔드 개발 컨벤션

## 코드와 타입

React 함수 컴포넌트와 TypeScript strict를 사용합니다. 컴포넌트는 PascalCase, 훅은 `useXxx`,
일반 함수·변수는 camelCase로 작성합니다. 타입은 `type`을 우선하고 확장·구현 계약이 필요한 경우
`interface`를 사용합니다. Props는 `XxxProps`, API 로컬 타입은 `Request`, `Response`, `ErrorDetail`
같이 역할이 드러나는 이름을 사용합니다.

공개 훅·API 래퍼·유틸은 입력과 반환 타입을 명시합니다. 근거 없는 `any`, 강제 타입 단언,
전역 타입 모음은 피하고 타입을 소유한 도메인 가까이에 둡니다. OpenAPI로 생성된 계약을 수기로
중복 선언하지 않습니다. 포맷은 이 디렉터리의 Prettier 기준인 공백 4칸·100자 폭·LF를 사용합니다.

프론트엔드 설치·실행·검사·빌드와 도구 설정은 모두 `frontend/` 안에서 관리합니다.
저장소 루트에 Node 패키지·잠금 파일·Prettier 설정을 두지 않습니다.

## 디렉터리와 의존 방향

다음은 기능이 추가될 때 사용하는 배치 기준입니다. 아직 필요한 기능이 없는 빈 디렉터리는 만들지 않습니다.

| 위치                                | 책임                                        |
| ----------------------------------- | ------------------------------------------- |
| `src/api/generated/`                | OpenAPI 생성 타입, 직접 수정하지 않음       |
| `src/api/<domain>/`                 | 도메인 API 요청과 오류 매핑                 |
| `src/hooks/api/<domain>/`           | 도메인 요청 수명주기·상태·액션              |
| `src/hooks/`                        | UI·인증 문맥·테마 등 비 API 훅              |
| `src/pages/<group>/`                | 페이지별 도메인 훅 호출·상태 연결·기능 조합 |
| `src/components/features/<domain>/` | props로 상태·액션을 받는 도메인 UI          |
| `src/components/ui/<category>/`     | 버튼·입력·카드·모달 등 공용 프리미티브      |
| `src/components/layout/`            | 앱 셸·내비게이션·페이지 프레임              |
| `src/styles/app.css`                | 전역 토큰·공용 외형·반응형 규칙             |
| `src/locales/`                      | 사용자 노출 문구                            |

API 흐름은 생성 타입 → `<domain>Api.ts`·`<domain>Error.ts` → `use<Domain>Api.ts` → 페이지입니다.
페이지·컴포넌트는 API 모듈을 직접 가져오지 않습니다. 도메인 훅은 페이지가 호출하고,
기능 컴포넌트는 상태·액션을 props로 받습니다. 공용 UI는 API·도메인 훅·페이지를 참조하지 않습니다.
단순 문법 배럴보다 도메인 소유권을 우선하고, 공용 UI의 공개 진입점은 `components/ui/index.ts`로 관리합니다.

## API와 상태

OpenAPI 명세와 생성 타입을 함께 관리하고 일반 빌드는 실행 중인 백엔드에 의존하지 않습니다.
알려진 오류 코드는 명시적으로 매핑하며, 알 수 없는 응답은 안전한 대체 메시지로 정규화합니다.
CSRF·접근 토큰·갱신·로그아웃은 백엔드 계약을 따르고 화면마다 새 규칙을 만들지 않습니다.

요청·loading·success·error는 도메인 훅이 소유합니다. 페이지가 이를 기능 컴포넌트에 전달하고,
동일 서버 상태를 컴포넌트나 전역 저장소에 다시 복제하지 않습니다. 응답이 늦게 도착하는 경우
취소·요청 세대·계정 변경을 확인해 이전 응답이 현재 상태를 덮지 않게 합니다.

입력 초안·필터·메뉴 상태는 가능한 한 로컬에 둡니다. 여러 소비자가 실제로 공유할 때 범위가 정해진
Context를 검토하며 전역 저장소를 선제 도입하지 않습니다. memo·useMemo·useCallback은 비용 있는
렌더링 경계나 참조 안정성이 필요한 경우에 적용합니다. 성능 개선을 주장할 때만 해당 측정 근거를 남깁니다.

## UI 구성과 스타일

새 UI를 만들기 전에 공용 UI·레이아웃·기존 기능 컴포넌트와 같은 유형의 기준 화면을 확인합니다.
재사용 가능한 컨트롤은 공용 컴포넌트를 먼저 추가·확장한 뒤 기능과 페이지에서 조합합니다.
페이지는 상태 연결·배치·도메인 문구에 집중하고 버튼·입력·모달을 화면마다 새로 만들지 않습니다.

CSS는 `src/styles/app.css` 한 곳에서 관리합니다. 색상·간격·곡률·크기는 공통 토큰을 사용하고
화면별 CSS, style 태그, JSX 외형 인라인 스타일을 추가하지 않습니다. 좌표·크기 측정처럼 동적인
기하가 꼭 필요한 예외는 공용 컴포넌트에 한정해 이유·소유자·검증을 문서화하고 검사 예외도 함께 갱신합니다.
현재 툴팁·드롭다운 포털의 좌표·너비·최대 높이는 해당 공용 컴포넌트가 DOM 측정으로 설정합니다.
이는 화면 경계를 맞추기 위한 기하 예외이며 색상·외형은 계속 공통 CSS가 소유합니다.

간격은 4·8·12·16·20·24·32px, 기본 컨트롤은 40px와 터치 44px를 기준으로 합니다.
곡률은 컨트롤 8px·카드 12px·패널 16px, 라벨·아이콘 간격은 8px, 카드 패딩은 16~24px를 사용합니다.
변형은 의미와 상태를 공유하되 모든 화면을 같은 크기로 강제하지 않습니다.

공용 UI를 추가하면 쇼케이스에 실제 컴포넌트의 기본·호버·포커스·선택·로딩·비활성·오류 예시를
해당 범위에 맞게 등록합니다. 샘플 전용 복제 UI를 만들거나 쇼케이스에서 실제 계정 변경 요청을 실행하지 않습니다.
긴 문구·숫자 변경에도 버튼 크기와 액션 위치가 흔들리지 않게 하고 disabled/loading은 중복 실행을 막습니다.

키보드 포커스·접근 가능한 이름·의미 있는 제목 구조를 유지합니다. 모달은 Escape·포커스 제한과 복원을,
툴팁은 호버·키보드·화면 경계와 스크롤을 고려합니다. 모션 줄이기 설정에서는 장식 전환·확대를 생략합니다.
입력 오류·필수 조치는 지속 UI에 표시하고 짧은 작업 결과만 토스트로 안내합니다.
테마는 공통 토큰을 사용하고 기본·호버·선택 상태의 글자 대비를 함께 확인합니다.

## 문구와 언어

사용자 노출 문구는 `src/locales/`의 키로 관리하고 화면에 하드코딩하지 않습니다. API 필드명·경로·CSS
클래스 등 내부 식별자는 리터럴을 사용할 수 있습니다. 사용자 입력과 서버 데이터는 번역문으로 취급하지 않습니다.
HTML 시작 문서의 제목·설명은 React 실행 전 정적 메타데이터라는 한정된 예외입니다.

기본 언어와 대체 언어는 한국어(`ko`)이며 영어(`en`) 리소스를 함께 관리합니다. 컴포넌트는
`useTranslation()`의 `t()`를 사용하고 두 사전에 동일한 키를 추가합니다. 한국어 사전을 기준으로
번역 키와 영어 필수 키를 타입 검사합니다. 언어 선택 UI·선택 저장·날짜/숫자 지역화는 #59에서
추가합니다. 사용자 문구는 간결한 존댓말을 사용하고 원본 서버 오류나 비밀값을 노출하지 않습니다.

## 화면 정합성과 검증

[화면 유형별 규칙](notes/page-families.md)에 따라 같은 유형의 기준 화면과 실제 배치를 비교합니다.
공용 컴포넌트 사용과 정적 검사 통과만으로 모든 화면의 정합성을 주장하지 않습니다.

검증은 변경 영향에 맞춥니다. 문구·문서 수정에 전체 빌드나 브라우저 조합 검사를 요구하지 않습니다.
코드 변경은 타입·린트·포맷, 실행·설정 변경은 빌드와 영향을 받는 대표 화면을 확인합니다.
새 UI 초안을 위해 별도 테스트 프레임워크·E2E·상세 작업 기록 양식을 도입하지 않습니다.
이미 통과한 검사는 관련 변경이나 새로운 실패가 없으면 반복하지 않습니다.

`frontend/`의 `pnpm check`는 타입·린트·UI 스타일·포맷 검사이며 `pnpm build`에도 타입 검사가 포함됩니다.
둘을 모두 실행할 필요가 없는 작업은 린트·포맷·빌드를 한 번씩 실행해 타입 검사 중복을 피할 수 있습니다.
ESLint는 직접 API import·컴포넌트의
도메인 훅 import·JSX 인라인 외형·JSX 텍스트 리터럴·페이지와 기능의 직접 컨트롤 생성을 검사합니다.
`pnpm ui:check`는 별도 CSS 파일 추가와 동일 규칙 안의 같은 속성·값 중복을 검사합니다.
동적 import, 별도 HTTP 호출, 다른 규칙 사이의 의미상 중복과 시각적 일치는 이 검사로 보장되지 않습니다.

현재 #60에는 정적 화면·한영 i18n·테마 미리보기·공용 CSS와 브랜드 자산을 포함합니다.
API·인증·영속 저장·실제 라우팅은 연결하지 않습니다. 미리보기의 로컬 화면·테마·언어 전환을
해당 업무 기능의 구현 완료로 기록하지 않습니다.
